Short context in case it helps prioritise:

- The driver targets the FVP Base Platform Trusted Entropy Source at
  0x7FE6_0000. Its register layout matches the existing Juno SoC TRNG
  (DDI 0515A), and the init / sample loop follows the same sequence
  TF-A already uses for Juno, so the flow should be familiar.

- I am consuming it from a no_std Rust SPMC running on FVP that needs a
  hardware entropy source available before any allocator is up. I would
  rather land this upstream than carry a fork.

- The patch is purely additive: one new `src/trusted_rng.rs` (267 lines),
  4 lines wired into `lib.rs`, one README line. Four unit tests cover
  init, single read, timeout / abort, and two consecutive reads.

One open decision I would like your call on before merge: the change
includes a base-r branch using the flipped memory layout, but I only
exercised the base-revc path. I do not currently have a base-r FVP
available to validate it on hardware, and I would rather not land a
silently-broken entropy source on a boot path nobody wants to debug.

Which of these do you prefer for this project:

  (a) gate the base-r path behind a feature flag, off by default, and
      mark it as unvalidated in the README;
  (b) drop the base-r branch from this change and submit it separately
      once it has been exercised on real base-r;
  (c) keep it as-is because someone on the review side will run a
      base-r FVP first.

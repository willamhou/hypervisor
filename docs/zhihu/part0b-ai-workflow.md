# 一个人 + AI 写 Hypervisor：工作流篇 — Claude Code 帮了什么忙，帮了什么倒忙

## 写在前面

上一篇讲了为什么做这个项目。这一篇讲怎么做——具体来说，一个人和 AI 搭档写裸机系统代码，日常的工作流是什么样的。

网上关于 AI 编程的文章不少，但大多是应用层的经验：写个 API、搭个前端、生成个 CRUD。裸机系统编程是另一回事——没有操作系统，没有标准库，寄存器写错一位就是安静挂起，"测试"就是启动模拟器看挂不挂。AI 在这种场景下的表现，和你在 StackOverflow 上看到的那些 ChatGPT 截图，是完全不同的体验。

这篇会尽量诚实。什么好用说什么好用，什么不行说什么不行。

---

## 什么是 Vibe Coding

这个词名声不太好。很多人一听"vibe coding"就觉得是"让 AI 写你看不懂的代码，然后祈祷它能跑"。

我实践的 vibe coding 不是那回事。一句话概括：**你掌控架构，AI 负责敲键盘。**

你用 ARM 架构层面的概念描述你要什么——"给每个虚拟 CPU 的中断分发器加 trap-and-emulate（陷入并模拟）"——AI 把它翻译成 Rust 代码。你逐行 review。不对的打回。对的你知道*为什么*对，因为你之前做过这个。

不过"vibe"的部分是真的。确实有这样的时刻：我用两句话描述一个功能，回来 200 行能跑的代码，只需要小调。这跟自己一行行写是质变的体验——你一直停留在设计层面思考，不用在架构和语法之间反复切换。

对应用层代码来说，这已经是常规操作了。但对裸机系统编程——ARM64 寄存器、无标准库的 Rust、内存映射 I/O——说实话我挺意外它能做到这个程度。

---

## 开发循环

理论上，每个功能都走这个流程：

```
1. 规划    → 写设计文档，标注架构约束
2. 测试    → 先写测试用例（TDD）
3. 实现    → AI 生成代码，人 review
4. 调试    → AI 提方案，人对照 ARM 手册验证
5. 审查    → 代码审查，查正确性和风格
6. 提交    → 写清楚的 commit message
```

实际呢？经常跳步。

早期的功能（Part 1-2，启动和 vCPU）几乎没有前期设计——我就描述想要什么，然后迭代到能跑。TDD（测试驱动开发）在裸机代码上更多是愿望——因为"测试"就是"启动 QEMU 看挂不挂"，你没法像写 Web 应用那样先写一个 `assert_eq!` 再写实现。

干净的六步循环是渐渐长出来的，大概从 Part 3（异常处理）开始。到那时候代码库复杂到一个程度：跳过设计直接写，意味着浪费几个小时走弯路。

git 历史诚实地反映了这一点。早期的 commit 是杂乱的大块头。后面的 commit 才有规律：`docs:`（设计）→ `feat:`（实现）→ `fix:`（调试）→ `docs:`（更新上下文文件）。**纪律不是预先设定的，是被痛苦逼出来的。**

---

## 问题来了：AI 没有记忆

六步循环听着挺好，但有个根本问题：**AI 没有跨会话的记忆。**

上午花一小时调出来一个 bug——比如"用 HPFAR_EL2 而不是 FAR_EL2 来取 guest 的中间物理地址"——下午开新会话，AI 可能又犯同样的错。你的经验在增长，但 AI 每次都是从零开始。

这个问题在项目前两周尤其严重。同一类 bug 反复出现，不是因为 AI 笨，而是因为它没有上下文。裸机 hypervisor 的上下文又特别难传递——不是"用 React hooks 而不是 class components"这种一句话就能说清的偏好，而是"QEMU virt 机器的 GICR 地址从 0x080A0000 开始，每个 CPU 占 0x20000，物理中断号 27 是虚拟定时器"这种具体到位域的细节。

怎么解决？

## CLAUDE.md — 项目的外部大脑

解决方案是一个文件：`CLAUDE.md`。Claude Code 每次启动新会话都会读它。

这是一个活文档——既是架构指南，也是机构记忆，更是一份"别再犯这个错"的清单。

里面有什么：

- **架构概览**：特权级模型、核心数据结构、异常处理流程图
- **构建命令**：每个 `make` 目标对应什么功能、开启什么编译选项
- **内存布局**：hypervisor、guest 内核、设备，每一段地址的用途
- **关键坑位**："用 HPFAR_EL2 不要用 FAR_EL2"、"永远不要改 guest 的 SPSR_EL2（处理器状态寄存器），否则内核自旋锁死锁"、"inject_spi() 不能拿 DEVICES 锁，否则死锁"
- **测试清单**：34 个测试套件，每个有多少断言

这个文件是怎么长出来的？模式永远一样：

1. 踩一个坑
2. 花一小时调
3. 修好
4. 在 CLAUDE.md 加一行，让 AI 下次别再犯

到项目结束，这个文件超过了 500 行——本质上是一份压缩的架构参考手册。没有人会从零坐下来写这种东西，但通过反复踩坑，它自然就积累出来了。

**一个意外的好处**：这个文件不只对 AI 有用。当我自己隔了几天回来看代码，也会先翻 CLAUDE.md 恢复上下文。它变成了整个项目的"机构记忆"，不分人和 AI。

## Agent 编排：让不同的 AI 干不同的活

Claude Code 支持专用 agent（可以理解为不同职能的 AI 角色）。不是每个都好用，以下是真正干了活的几个：

| Agent | 做什么 | 实际效果 |
|-------|-------|---------|
| **planner** | 拆解功能、设计架构 | Part 5（多核）之后必需。早期用了反而多余——设计文档写了也没人看。 |
| **tdd-guide** | 强制先写测试再写实现 | 纯逻辑代码好用（比如 FF-A 协议解析）。涉及硬件交互的没法用——你没法在没有 QEMU 的情况下测中断注入。 |
| **code-reviewer** | 审查代码正确性和风格 | 真抓到过 bug。每次都值得跑。 |
| **build-error-resolver** | 修编译错误 | 一半一半。类型错误行，链接错误不行。 |
| **architect** | 评估设计方案的权衡 | 偶尔用。多虚拟机内存布局时帮了忙。 |

agent 的分离比你想的重要。planner 看不到测试代码，reviewer 看不到设计文档。这种**聚焦**让每个 agent 不会被无关信息淹没。

反面例子：如果你把设计文档、全部源码、测试代码、调试日志全塞给一个 AI 会话，它的注意力会被稀释。我早期就犯过这个错——一个超长的会话里又改设计又写代码又调 bug，AI 的输出质量肉眼可见地下降。

## AI 擅长什么

经过 30 天密集使用，总结下来 AI 真正好用的场景有四类。

**第一，模板和结构代码。** ARM 寄存器定义、50 行的 `match`（模式匹配）分支、测试框架搭建。这类代码写起来枯燥但不需要什么创造力，AI 的速度是人的 5-10 倍，而且不会因为无聊犯低级错误。

**第二，对照规范写代码。** 我说"实现 FF-A v1.1 规范 Table 5.19 的内存描述符解析"，AI 能直接输出能跑的代码——结构体偏移量正确，packed（紧凑内存布局）用了 `read_unaligned`（非对齐读取）。它能把规范文档装进上下文窗口，直接翻译成代码。这是人最痛苦的活之一，对着 PDF 一个字段一个字段地抄，AI 做这个又快又准。

**第三，模式复制。** 一旦一个 virtio 设备（virtio-blk，虚拟块存储）端到端跑通了，加 virtio-net（虚拟网络）几乎是自动的。AI 认出了代码结构模式，照搬过去，只改了设备特定的部分。从零写 virtio-net 可能要一天，有了 virtio-blk 做参照只要一两个小时。

**第四，调试方向。** 给 AI 一个异常综合征值（ESR_EL2）加上症状描述——"guest 启动到一半挂了，ESR 值是 0x96000047"——它判断 bug 类别经常是对的："看着像 Stage-2 权限错误，查一下 S2AP（Stage-2 访问权限）位。"具体怎么修不一定对，但**该往哪个方向看**基本没错。这对裸机调试特别有价值——当你面对一个安静的挂起，连该从哪里开始查都不知道的时候，一个靠谱的方向比什么都重要。

## AI 不擅长什么

说完好的，说不好的。以下是 AI 真正让我栽跟头的几个场景。

### HPFAR_EL2：一天的代价

这是经典案例，值得展开讲。

当 guest 操作系统的 MMU（内存管理单元）开启后，guest 访问一个未映射的地址会触发 Stage-2 fault，陷入 hypervisor 处理。这时候 hypervisor 需要知道 guest 想访问的**中间物理地址（IPA）**是什么，才能模拟对应的设备。

ARM 提供了两个寄存器：`FAR_EL2` 和 `HPFAR_EL2`。关键区别是：guest MMU 开启后，`FAR_EL2` 给的是 guest 的**虚拟地址**，不是 IPA。你必须用 `HPFAR_EL2` 才能拿到正确的 IPA。

AI 一直建议修 MMIO（内存映射 I/O）分发层的代码——"地址匹配逻辑有问题"、"设备注册的地址范围不对"——因为从它的视角看，guest 访问了一个"错误的地址"。但真正的问题在上游：IPA 提取用错了寄存器，所以不管下游怎么改都是错的。

花了整整一天。AI 提了至少五个不同的修复方案，全都在错误的层面上。最后是我翻 ARM 架构手册，看到 `HPFAR_EL2` 的描述，才意识到问题在哪。

**教训**：AI 能在它看到的代码范围内推理，但当 bug 的根因在它的"注意力"之外时，它会在错误的层面反复打转。

### 并发：三次"加个锁"

多物理核模式（multi-pCPU）下，`inject_spi()`（注入共享外设中断）这个函数有一个死锁问题。

背景是：这个函数是从设备管理器（`DEVICES`）的锁**里面**被调用的。它需要查找中断的路由信息——"这个中断应该发给哪个 CPU？"——而路由信息也存在 `DEVICES` 里。如果它再去拿同一把锁，就死锁了（Rust 的 SpinLock 不支持重入）。

AI 连着提了三次方案，全是"加个锁"的变体——"用一个单独的锁保护路由表"、"用 RwLock 替换 SpinLock"、"在调用前先释放外层锁"。每一个都没解决根本问题，有的甚至引入新的竞争条件。

最后的解决方案是：**绕过锁，直接读硬件。** EL2（hypervisor 层级）不受 Stage-2 地址翻译的限制，可以直接读物理 GIC 的路由寄存器（GICD_IROUTER），不需要经过软件的设备管理器。这个方案 AI 提不出来，因为它需要理解"EL2 绕过 Stage-2"这个 ARM 硬件特性，以及"为什么读硬件在这里是安全的"。

**教训**：AI 对并发问题的直觉是"加锁"。当正确答案是"绕过锁"或"重新设计数据流"时，AI 很难自己想到。

### 构建系统：环节太多

TF-A（ARM 安全固件）的构建流水线大概是这样的：

```
Makefile → Docker 容器 → 交叉编译 → FIP 打包 → SP 镜像 UUID 字节序转换 → 烧录
```

每一个环节 AI 都能单独修对。但当问题跨越多个环节时——比如"为什么 SP 镜像没有被打包进 FIP？"——AI 没法端到端地推理整条流水线。它会修 Makefile 里的路径，但不知道 Docker volume 里缓存了旧的构建产物；或者它修对了 SP 的 UUID，但不知道 `sp_layout.json` 里的路径是相对于 JSON 文件位置而不是项目根目录。

**教训**：AI 的推理半径有限。当一个问题需要跨越 5-6 个配置文件和 2-3 个构建环境时，人必须自己理清全貌。

### 假阳性自信：测试通过 ≠ 正确

这个最隐蔽。有时候 AI 生成的代码通过了所有测试——但只是碰巧对的。测试没覆盖到真正重要的边界。

举个例子：FF-A 的 `MEM_SHARE`（内存共享）在单元测试里用了一个硬编码的地址，而这个地址在测试环境下恰好已经映射了。但在真实的 guest 场景下，这个地址可能没有被映射——于是 Stage-2 walker（页表遍历器）会读到无效的页表项，silent corruption（静默数据损坏）。

AI 对此毫无感觉。它看到测试绿了就认为搞定了。**人的职责是问"这是因为正确的原因才对的吗？"** 然后补上缺失的测试。

**教训**：AI 对测试覆盖率的"直觉"远不如人。它能写测试，但不能判断测试是否覆盖了关键路径。

## 数字

30 天的粗略统计：

- **193 个 commit**（平均每天 6.4 个）
- **约 457 个测试断言**，分布在 34 个测试套件里
- **人的贡献**：约 30%——架构决策、翻 ARM 手册、调试集成问题、review 每一行 AI 生成的代码
- **AI 的贡献**：约 70%——代码生成、写测试、模板代码、初步调试方向
- **CLAUDE.md**：从 0 行长到 500 多行，后期回头精简压到 ~280 行（信息密度优先）

但 30/70 这个比例有误导性。那 30% 的人类工作承担了不成比例的**承重**——就像一座桥，70% 的材料是混凝土，但承重的是那 30% 的钢筋。如果钢筋不对，混凝土再多也会塌。

AI 一个人做不了这个项目。但我一个人也不可能 30 天做完。

## 给想试 AI 辅助系统编程的人的建议

如果你也在做底层系统开发，想试试 AI 搭档，以下是我踩完坑后的几条建议：

**1. 写好你的上下文文件。** 不管用什么 AI 工具，第一件事是把项目的架构、内存布局、关键约束写成一个文件，让 AI 每次都读。这比任何 prompt 技巧都重要。

**2. 拆小任务。** "实现 GICv3 虚拟化"太大了。"实现 GICD ISENABLER 寄存器的 trap-and-emulate"刚好。AI 在单一、明确的任务上表现最好。

**3. 不要跳过 review。** AI 生成代码的速度快到你会有一种"它大概率是对的"的错觉。不是的。裸机代码里 AI 犯的每个错误都是安静的——不会崩溃，不会报错，只会在三个 feature 之后以一种完全无关的方式爆发出来。

**4. 用 agent 分离关注点。** 不要在一个会话里又设计又写码又调试。让 planner 做设计，让 coder 写代码，让 reviewer 审查。每个角色的上下文越干净，输出质量越高。

**5. 硬件相关的 bug，自己查手册。** AI 对 ARM 架构概念的理解是扎实的，但对具体寄存器位域的记忆不一定准。当你遇到安静挂起，最靠谱的做法永远是翻 ARM Architecture Reference Manual，而不是让 AI 猜。

## 几个概念

如果你对 hypervisor 领域不太熟悉，这里简单铺垫几个概念，方便后面阅读。

**Hypervisor（虚拟机监控器）** 是一层运行在硬件和操作系统之间的软件。它把一台物理机"切"成多个虚拟机，每个虚拟机以为自己独占硬件。你用的云服务器，底下大概率就是 hypervisor 在管。

**Type-1（裸机型）** 指的是 hypervisor 直接跑在硬件上，不依赖一个宿主操作系统。相对的 Type-2（比如 VirtualBox）是跑在 Windows/Linux 上面的应用程序。Type-1 性能更好，安全性更高，但开发难度也高得多——你面对的是裸硬件，没有操作系统帮你管内存、管中断、管调度。

**ARM64** 是 ARM 公司的 64 位处理器架构。你的手机、平板、越来越多的服务器和笔记本（比如 Apple M 系列）都是 ARM64。ARM 定义了一套**特权级别**（Exception Level）：

- **EL0**：用户态应用
- **EL1**：操作系统内核
- **EL2**：Hypervisor——这是我们写代码的地方
- **EL3**：安全监控器（Secure Monitor），负责在"安全世界"和"普通世界"之间切换

**Stage-2 翻译**是 ARM 硬件提供给 hypervisor 的核心机制。简单来说，guest（虚拟机里的操作系统）以为自己在访问物理地址 A，但硬件会悄悄把 A 翻译成真正的物理地址 B。这样 hypervisor 就能控制 guest 能看到哪些内存、不能看到哪些。

**GICv3（通用中断控制器 v3）** 是 ARM 平台的中断管理硬件。中断就是硬件告诉 CPU "有事发生了"的机制——键盘按键、网络数据到达、定时器超时。虚拟化中断是 hypervisor 最复杂的部分之一。

**FF-A（Firmware Framework for Arm）** 是 ARM 定义的一套固件通信协议，用于安全世界和普通世界之间的标准化通信。可以理解为"虚拟机和安全固件之间的 API 规范"。

**TF-A（Trusted Firmware-A）** 是 ARM 的开源安全固件参考实现，运行在 EL3，负责从上电到操作系统启动的整条引导链。

**pKVM（protected KVM）** 是 Google 在 Android 上推的虚拟化方案，把 Linux KVM 的一部分提升到 EL2 运行，隔离 guest 和 host。我们的最终目标是让 pKVM 跑在普通世界（EL2），我们的 hypervisor 跑在安全世界（S-EL2），两者通过 FF-A 协作。

有了这些概念，后面的内容就不会太突兀了。如果你已经熟悉这些，跳过这一节。

## 背景：第一个 Hypervisor

我目前在做 AI 创业。在此之前，在大厂和创业公司都待过，始终被技术栈的最底层吸引——内核、hypervisor、固件。就是那种寄存器写错一位就安静挂掉、"printf 调试"意味着手动往 UART（串口）写字节的代码。

在某大厂，我带过一个 3-4 人的团队，从零用 Rust 写了一个裸机 ARM64 hypervisor。从第一行代码到通过 CCRC 安全认证再到商用部署，大约一年。其中开发阶段 10 个月左右。据我们所知，这是世界上第一个通过 CCRC 认证的 Rust 安全 hypervisor（SPMC，即安全分区管理器）。

那段经历留下了很深的印记。

**复杂度永远不在你以为的地方。** hypervisor 的核心循环是"陷入-模拟-恢复"（trap-emulate-resume）：guest 执行到某条特权指令，硬件陷入 hypervisor，hypervisor 模拟该操作，然后恢复 guest 继续跑。这个循环本身？一个周末就能写完。然后你花接下来 9 个月跟周边的一切搏斗——GICv3 中断注入的时序、几十种异常类型的分类处理、一个只在第 4 个虚拟 CPU 做 SMP（多核）压力测试时才复现的页表损坏。核心循环大概只占 5% 的工作量。

**ARM 架构手册有 12000 页，你大概需要用到其中 3000 页。** 在 EL2 出了问题，没有调试器，没有堆栈跟踪，没有友好的错误信息。只有安静的挂起。或者更惨——每 200 次启动挂一次。你会学着像医生看心电图一样读异常综合征值（ESR_EL2），从一个 32 位的数字里判断是哪种 fault、哪个寄存器、哪条指令出的问题。

**Rust 赌对了。** 我们很早就押注——`no_std`（无标准库）、自定义编译目标、手写寄存器访问。生态不成熟（现在依然——没有现成的中断控制器驱动，没有 ARM 指令封装库）。但回报是实打实的：10 个月开发，零次内存释放后使用（use-after-free）。换成 C 写 hypervisor，这个数字不可能。

## 一个挥之不去的想法

2025 年年中，脑子里反复转着同一个念头：如果从零重建那个 hypervisor 呢？

我们已经证明了 Rust 做得了生产级 hypervisor。但我们也切身体会过那种工程量。ARM 的架构面太大了——每一个边界情况，某个只在特定 CPU 处于特定电源状态时才有意义的中断控制器寄存器，某个只在虚拟机和 hypervisor 的 MMU（内存管理单元）同时开启时才触发的地址翻译错误，都必须正确处理。没有"差不多就行"这回事。

一个人能把这段旅程的核心复刻出来吗？大概能吧，但要好几个月。我还有创业公司要经营。

搁置了。

## 一个晚上的 boot.S

2025 年底，我日常在用 Claude Code 做应用层的活——API、前端，不算什么硬核的东西。

然后有天晚上心血来潮，让它写一个 ARM64 EL2 入口的 `boot.S`（引导汇编）——栈设置、BSS（未初始化数据段）清零、跳转到 Rust。

架构层面写对了。寻址指令用对了，代码段布局放对了，空循环也对。我带过的工程师，有人第一次写这个也会搞错。

于是我继续加码。"写一个 2MB 粒度的 Stage-2 地址映射。"对了。"用硬件陷阱拦截 guest 的 WFI（等待中断）指令，在异常向量里处理。"也对了，包括把程序计数器往前推 4 字节（跳过被陷入的指令）。

它分得清操作系统层级（EL1）和 hypervisor 层级（EL2），能推理页表基地址寄存器的位域编码，能解释 Stage-2 翻译为什么需要单独的寄存器来拿中间物理地址（IPA）。不完美——有些盲区后来让我们付出了好几天的代价——但基础是在的。

想法又回来了。不过这次问题变了。不是"AI 能不能写 hypervisor？"——这个问题就问错了。正确的问题是：**AI 能不能把一个 3-4 人团队 10 个月的活，压缩到一个人几周干完？**

## 实验

我定了一个目标：从零重建核心的 hypervisor 旅程，用 Rust，Claude Code 当搭档。不是玩具——一个真正的 Type-1 裸机 hypervisor，能启动 Linux，搞得定多核调度，做虚拟存储 I/O，实现 ARM 的 FF-A 固件通信框架。

规则：
- **只用 Rust**（加上启动和异常处理必要的 ARM64 汇编）
- **不碰现有代码**——不 fork 开源项目，不从生产版本抄
- **AI 当结对搭档**——Claude Code 负责规划、实现、测试、调试
- **全程留痕**——每个 commit，每个设计决策，每个 bug

2026 年 1 月 26 日，第一个 commit。2 月 24 日，pKVM 带着我们的安全分区管理器在 S-EL2 跑起来了，FF-A v1.1 完全可用。

前后 30 天，193 个 commit。

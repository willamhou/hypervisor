# Implementation: The First 4 Files

The first working hypervisor needs exactly 4 handwritten files: assembly boot code, a linker script, a Rust entry point, and a build script. Everything else is generated by the toolchain.

## boot.S — The Entry Point

The CPU starts executing here. Before any Rust code can run, we need a stack and zeroed BSS:

```armasm
.section .text.boot
.global _start

_start:
    // Set up stack (16KB, grows downward)
    adr     x0, stack_top
    mov     sp, x0

    // Clear BSS section
    adr     x0, __bss_start
    adr     x1, __bss_end
clear_bss:
    cmp     x0, x1
    b.ge    clear_bss_done
    str     xzr, [x0], #8
    b       clear_bss
clear_bss_done:

    // Jump to Rust
    bl      rust_main

halt:
    wfe
    b       halt
```

Three things happen:

1. **Stack setup** — `adr` loads the address of `stack_top` (defined in BSS). The stack grows downward, so we point SP at the top of a 16KB region. ARM64 requires 16-byte stack alignment, enforced by `.align 16` on the stack section.

2. **BSS zeroing** — Rust's `static mut` variables and uninitialized globals live in BSS. The ELF loader doesn't zero them for us (there's no loader — QEMU loads the raw binary). We zero the range `[__bss_start, __bss_end)` 8 bytes at a time using `str xzr`.

3. **Jump to Rust** — `bl rust_main` calls the `#[no_mangle] pub extern "C" fn rust_main()` in Rust. If it returns (it shouldn't), we fall through to `halt` which loops on WFE (Wait For Event).

Note: the first version of `boot.S` also checked `CurrentEL` to verify we're at EL2. The fix commit (`b2ff49f`) removed it — it added complexity without value since there's no fallback path.

## linker.ld — Memory Layout

```ld
ENTRY(_start)

SECTIONS
{
    . = 0x40000000;   /* QEMU virt: RAM starts here */

    .text : {
        KEEP(*(.text.boot))   /* boot.S first! */
        *(.text .text.*)
    }

    .rodata : { *(.rodata .rodata.*) }
    .data   : { *(.data .data.*) }

    .bss : {
        __bss_start = .;
        *(.bss .bss.*)
        *(.bss.stack)
        *(COMMON)
        __bss_end = .;
    }

    /DISCARD/ : { *(.comment) *(.eh_frame) }
}
```

Key decisions:

- **Base address `0x40000000`** — QEMU's `virt` machine places RAM at 0x40000000. When using `-kernel`, QEMU loads the binary to this address. (Later, when we add TF-A boot, this moves to `0x40200000` to avoid the QEMU-generated DTB at 0x40000000.)

- **`KEEP(*(.text.boot))`** — ensures `_start` from `boot.S` is the very first code in the binary. Without `KEEP`, the linker might discard it as "unused." Without placing it first, the CPU would begin executing whatever random function happens to be at the load address.

- **BSS includes the stack** — the 16KB stack lives in `.bss.stack`, inside the BSS range. This means our BSS-zeroing loop also zeros the stack, which is fine (it's uninitialized anyway).

## rust_main() — First Rust Code

```rust
#![no_std]
#![no_main]

use core::panic::PanicInfo;

fn uart_puts(s: &[u8]) {
    unsafe {
        let uart_base = 0x09000000usize;
        for &byte in s {
            core::arch::asm!(
                "str {val:w}, [{addr}]",
                addr = in(reg) uart_base,
                val = in(reg) byte as u32,
                options(nostack),
            );
        }
    }
}

#[no_mangle]
pub extern "C" fn rust_main() -> ! {
    uart_puts(b"Hello from EL2!\n");
    loop { unsafe { core::arch::asm!("wfe"); } }
}

#[panic_handler]
fn panic(_info: &PanicInfo) -> ! {
    loop { unsafe { core::arch::asm!("wfe"); } }
}
```

Several things to note:

- **`#![no_std]` + `#![no_main]`** — no standard library, no `fn main()`. This is a freestanding binary.

- **`uart_puts` uses inline assembly** — The PL011 UART on QEMU `virt` is at `0x09000000`. Writing a byte to offset 0x00 (the Data Register) sends it to the serial console. We use `str` (store register) via inline `asm!` because at this point we don't have a proper UART driver yet. The `{val:w}` format uses the 32-bit `w` register variant because PL011 expects 32-bit writes.

- **`#[no_mangle] pub extern "C"`** — so `boot.S` can call it via `bl rust_main`. Without `no_mangle`, Rust mangles the symbol name. Without `extern "C"`, the calling convention might differ.

- **`-> !`** (never returns) — `rust_main` loops forever. If it somehow returned, `boot.S` catches it in the `halt` loop.

The first commit (`609459b`) had a more elaborate UART driver (`src/uart.rs`) with `fmt::Write` support, `print!`/`println!` macros, and TX FIFO wait. The fix commit (`b2ff49f`) stripped it down to the minimal inline-assembly version above. Why? The elaborate version had linking issues — the `fmt` machinery pulled in more of `core` than a bare-metal binary could support at that point. Simpler was better for Milestone 0.

## build.rs — The Glue

```rust
fn main() {
    let out_dir = PathBuf::from(env::var("OUT_DIR").unwrap());

    // Cross-compile boot.S with aarch64-linux-gnu-gcc
    Command::new("aarch64-linux-gnu-gcc")
        .args(&["-c", "arch/aarch64/boot.S", "-o",
                boot_o.to_str().unwrap(),
                "-nostdlib", "-ffreestanding"])
        .status().expect("Failed to compile boot.S");

    // Archive into libboot.a
    Command::new("aarch64-linux-gnu-ar")
        .args(&["crs", boot_a.to_str().unwrap(),
                boot_o.to_str().unwrap()])
        .status().expect("Failed to create archive");

    // Tell Cargo to link it
    println!("cargo:rustc-link-search=native={}", out_dir.display());
    println!("cargo:rustc-link-lib=static=boot");
}
```

This is the bridge between ARM64 assembly and Rust:

1. `aarch64-linux-gnu-gcc` cross-compiles `boot.S` into an object file
2. `aarch64-linux-gnu-ar` archives it into `libboot.a`
3. Cargo links `libboot.a` with the Rust binary

The `_start` symbol from `boot.S` becomes the ELF entry point (specified by `ENTRY(_start)` in the linker script). Cargo doesn't know about assembly files natively, so `build.rs` handles the cross-compilation step.

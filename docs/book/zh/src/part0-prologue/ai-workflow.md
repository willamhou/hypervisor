# AI 工作流 — 用 Claude Code 做 Vibe Coding

## 什么是 Vibe Coding？

这个词名声不太好。很多人一听"vibe coding"就觉得是"让 AI 写你看不懂的代码"。我这里不是那回事。

我实践的 vibe coding 是这样的：**你掌控架构，AI 负责敲键盘。** 你用 ARM 层面的概念描述你要什么——"给每个 vCPU 的 Redistributor 状态加 GICR trap-and-emulate"——AI 把它翻译成 Rust 代码。你逐行 review。不对的打回。对的你知道*为什么*对，因为你之前做过这个。

不过"vibe"的部分是真的。确实有那种时刻：我用两句话描述一个 feature，回来 200 行能跑的代码，只需要小调。这跟自己写是质变的体验。你一直待在设计层面思考，不用在架构和语法之间来回切换。

对应用层代码来说，这已经是常规操作了。但对裸机系统编程——ARM64 寄存器、`no_std` Rust、MMIO——说实话我挺意外它能做到这个程度。

## 开发循环

理论上，每个 feature 都走这个流程：

```
1. 规划    → 设计文档，标注架构约束
2. 测试    → 先写测试（TDD）
3. 实现    → AI 生成代码，人 review
4. 调试    → AI 提方案，人对照 ARM 手册验证
5. 审查    → 代码审查，查正确性和风格
6. 提交    → 规范化的 commit message
```

实际呢？经常跳步。早期的 feature（Part 1-2）几乎没有前期设计——我就描述想要什么，然后迭代到能跑。TDD 在裸机代码上更多是愿望——因为"测试"就是"启动 QEMU 看挂不挂"。干净的六步循环是渐渐长出来的，大概从 Part 3（异常处理）开始，那时候代码库复杂到跳过设计就意味着浪费几小时。

git 历史诚实地反映了这一点。早期的 commit 是杂乱的 `feat:` 大块头。后面的 commit 才有规律：`docs:`（设计）→ `feat:`（实现）→ `fix:`（调试）→ `docs:`（更新 CLAUDE.md）。纪律随项目一起成长。

## CLAUDE.md — 项目大脑

项目里最重要的文件是 [`CLAUDE.md`](https://github.com/willamhou/hypervisor/blob/main/CLAUDE.md)。Claude Code 每次开会话都会读它。这是一个活文档——一半是架构指南，一半是机构记忆，一半是"别再犯这个错"清单。

里面有什么：
- **架构概览**：特权模型、核心抽象、异常处理流
- **构建命令**：每个 `make` target 和 feature flag 的文档
- **内存布局**：hypervisor、guest、设备的地址映射
- **关键坑位**："用 HPFAR_EL2 不要用 FAR_EL2 取 IPA"、"永远不要改 guest 的 SPSR_EL2"、"inject_spi() 不能拿 DEVICES 锁"
- **测试清单**：33 个测试套件的断言数

这个文件是有机生长出来的。模式永远一样：踩一个坑，花一小时调，修好，然后在 CLAUDE.md 加一行，让 AI 下次别再犯。到最后超过了 500 行——本质上是一份压缩的架构手册。没有人会从头写这种东西，但通过踩坑自然就积累出来了。

## Agent 编排

Claude Code 支持专用 agent。真正干活的几个：

| Agent | 角色 | 评价 |
|-------|------|------|
| **planner** | 设计架构，拆解 feature | Part 5+（SMP）必需。早期用了反而多余。 |
| **tdd-guide** | 先写测试再实现 | 纯逻辑代码（FF-A 解析）好用。涉及硬件的没用。 |
| **code-reviewer** | 查正确性和风格 | 真抓到过 bug。每次都值得跑。 |
| **build-error-resolver** | 修编译错误 | 一半一半。类型错误行，链接错误不行。 |
| **architect** | 评估设计权衡 | 偶尔用。多 VM 内存布局时帮了忙。 |

agent 的分离比你想的重要。planner 看不到测试代码。reviewer 看不到设计文档。这种聚焦让每个 agent 不会被无关信息淹没。

## AI 擅长什么

**模板和结构代码。** 寄存器定义、50 行的 `match` 分支、测试框架。写起来枯燥但不需要什么创造力的代码，AI 秒杀。

**对照规范写代码。** "实现 FF-A v1.1 Table 5.19 的描述符解析" → 能跑的代码，结构体偏移量正确，packed 布局用了 `read_unaligned`。AI 能把规范装在上下文里直接翻译。

**模式复制。** 一旦一个 virtio 设备（virtio-blk）端到端跑通了，加 virtio-net 几乎是自动的。AI 认出了模式，稍微调整就搬过去了。

**调试方向。** 给一个 ESR_EL2 值加上症状描述，AI 判断 bug 类别经常是对的——"看着像 Stage-2 权限错误，查一下 S2AP 位。" 具体怎么修不一定对，但该往哪看基本没错。

## AI 不擅长什么

**HPFAR_EL2 那个 bug。** 经典案例。guest MMU 开启后，`FAR_EL2` 给的是 guest 的*虚拟地址*，不是 IPA。你得用 `HPFAR_EL2` 拿 IPA。AI 一直建议改 MMIO 分发层，但真正的问题在 IPA 提取。花了整整一天。（Part 4 有完整故事。）

**并发。** multi-pCPU 上 `inject_spi()` 的死锁——这个函数是从 `DEVICES` 锁*里面*被调用的，所以不能再去拿同一把锁查 SPI 路由。AI 连着提了三次"加个锁"的方案，直到我解释了重入问题。

**构建系统集成。** TF-A 的构建（Makefile → Docker → FIP 打包 → sp_layout.json → UUID 字节序转换）环节太多。AI 能孤立地修任何一个环节，但没法端到端地推理整条流水线。

**假阳性自信。** 有时候 AI 生成的代码通过了所有测试，但只是碰巧对——测试没覆盖到真正重要的边界。人的职责就是问"这是因为正确的原因才对的吗？"然后补上缺失的测试。

## 数字

30 天的粗略统计：

- **193 个 commit**（~6.4 个/天）
- **约 282 个测试断言**，33 个测试套件
- **人的贡献**：~30%——架构决策、查 ARM 手册、调试集成问题、review 每一行 AI 生成的代码
- **AI 的贡献**：~70%——代码生成、写测试、模板代码、初步调试方向
- **CLAUDE.md**：从 0 行到 500+ 行的累积上下文

但 30/70 这个比例有误导性。那 30% 的人类工作承担了不成比例的*承重*。AI 一个人做不了这个项目。但我一个人也不可能 30 天做完。

# 个人背景

我的职业生涯横跨 AI 和系统软件两个领域。

目前是一家 AI 创业公司的联合创始人。在此之前，我在大厂和创业公司都待过，始终被技术栈的最底层所吸引——内核、hypervisor、固件。

## 第一个 Hypervisor

在某大厂，我带领一个 3-4 人的团队，从零开始用 Rust 构建了一个裸机 ARM64 hypervisor。完整的旅程——从第一行代码到通过 CCRC 安全认证再到商用部署——大约花了一年。其中开发阶段大概 10 个月。据我们所知，这是世界上第一个通过 CCRC 认证的 Rust 安全 hypervisor（SPMC）。

那段经历留下了很深的印记。有几件事我至今都记着：

复杂度永远不在你以为的地方。陷入-模拟-恢复的核心循环？那是最简单的部分，一个周末就能写完。然后你花接下来 9 个月跟周边的一切搏斗——GICv3 的 list register 注入调对、14 种不同的 ESR_EL2 异常类型、一个只在第 4 个 vCPU 的 SMP 压力下才复现的 Stage-2 页表损坏。核心循环大概只占 5% 的工作量。

ARM 架构手册有 12000 页，你大概需要用到其中 3000 页。在 EL2 出问题的时候，没有调试器，没有堆栈跟踪，没有友好的错误信息。只有安静的挂起。或者更惨，每 200 次启动挂一次。你会学着像医生看心电图一样读 ESR_EL2 的综合征值。

Rust 赌对了。我们很早就押注了——`no_std`、自定义 target、手写的寄存器访问。生态不成熟（现在还是——没有现成的 GIC 驱动，没有 ARM intrinsics crate）。但回报是实打实的：10 个月的开发周期，零 use-after-free。如果用 C 写 hypervisor，这个数字不可能。

测试一直在救命。没有靠谱的测试框架，每次改动都像在翻硬币。EL2 的 bug 不会给你一个漂亮的报错——它会默默污染 guest 状态，然后等三个 feature 之后，某个完全无关的东西突然挂了。

## 双重背景

AI 那边的经历给了我一个意想不到的东西：对"不精确"的容忍度。ML 工程师快速原型、快速迭代。系统工程师把规范读三遍才动手写第一行。两种都对，看你在什么阶段。

这个项目两种都需要。Hypervisor 要求精确——寄存器某一位搞错了 guest 就挂。但 AI 辅助的工作方式要求你愿意尝试可能不行的东西，扔掉不行的，继续走。
